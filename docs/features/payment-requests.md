# Payment requests (bills)

A *payment request* is a supplier bill a company wants paid: who, how much, for what,
dated, with the invoice attached. The API is `/api/bills/*` (`bills/api.py`, services in
`bills/services/bill_service.py`); the model is `Bill` with its `BillLine`s (`bills/models.py`,
tables `bill`, `bill_line`), scoped to the entity of the request.

## Lifecycle

```
draft ──submit──▶ submitted ──payments──▶ partially_paid ──▶ paid
                     │  ▲
              return │  │ un-return
                     ▼  │
                  returned ──void──▶ void
draft ──delete──▶ (row removed)      any non-draft ──delete──▶ void
```

`Bill.Status`: `draft`, `submitted` (shown as **Payment Requested**), `returned`,
`partially_paid`, `paid`, `void`. `Bill.PublishStatus` is a second axis: `draft` (Not
Published), `published`, `failed`.

- **Draft** — `POST /api/bills/draft/` and `PUT /api/bills/{id}/draft` save without
  validation (anything may be missing).
- **Submit** — `POST /api/bills/submit/` (create-and-submit) or `POST /api/bills/` runs
  `validate_for_submission`: a contact, an amount above zero, an invoice date, a due date
  and **at least one attachment** are required; the errors come back together (422) in
  the words the dialog shows.
- **Edit** — `PUT /api/bills/{id}`; the response carries the payment-synced status and
  `amount_due`. A paid or partially-paid bill needs an elevated role to be edited.
- **Return / un-return / void** — `POST /api/bills/{id}/return/` with `status:
  "payment_requested"` (submitted → returned), `"returned"` (returned → submitted) or
  `"void"` (returned → void); elevated roles only.
- **Delete** — `DELETE /api/bills/{id}`: a draft is hard-deleted; anything else becomes
  `void` (`bills/tests/test_void_transitions.py`, `test_bill_immutability.py`).
- Payments move the status between `submitted`, `partially_paid` and `paid`
  ([payments.md](payments.md)).

## Fields worth knowing

- `bill_number` — the supplier's invoice number; `reference` — ours, auto-generated by
  `GET /api/bills/suggested-reference/`: `MBI` + three letters of the entity name +
  `-HHMMSSDDMMYY` in Hong Kong time, unique among the entity's non-voided bills
  (`bill_reference_generator.py`); a duplicate is refused with a field error.
- `contact` / `contact_id` — the supplier, one of the entity's synced Xero contacts
  (`xero_contact_sync`; `GET /api/entity-bill-contacts/` lists them, `POST` creates one in
  Xero and caches it); `xero_account_code` — from the entity's bill account list
  (`entity_bill_account_xero`, synced by Minty); `currency_code` — the entity's currency;
  `invoice_date`, `due_date`, `description`, `amount`, `amount_paid`.
- Lines: one `bill_line` per bill today (description, quantity, unit amount, account code).

## Listing

`GET /api/bills/` — the entity's bills, paged (`page`, `page_size`, `sort_by`), with the
paid date derived from the last completed payment; filters `status`, `search` (supplier,
reference, description), `contact`, `amount_min` / `amount_max`, and a date range
(`date_field`, `date_from`, `date_to`). The frontend's tabs map to `status` (`All`,
Payment Requested, Partially Paid, Returned, Paid, Draft, Voided) and its Xero filter
reads `published` client-side.

## Every change is audited

`bills/services/audit_service.log_audit` writes a `bill_audit` row for created / edited /
submitted / status changed / marked paid / voided / published to Xero / attachment
uploaded or deleted / payment created, updated, deleted; `GET /api/bills/{id}/audit`
returns them and the frontend's Activity history renders them (`bills/api_audit.py`).
